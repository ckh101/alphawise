# 桌面客户端构建方案

版本：0.1.0 | 更新日期：2026-06-24

---

## 适用范围

本文档说明如何从源码构建 Windows / macOS 安装包（NSIS `.exe` / `.dmg`），以及构建背后的关键架构约束。

> 配套的开发环境搭建见 `docs/开发部署文档.md`。本文聚焦**生产打包**。

---

## 1. 构建产物架构

```
安装包 (NSIS exe / dmg)
└─ win-unpacked/ 或 *.app
   ├─ 灵智投研助手.exe / Electron.app      ← Electron 28 壳（含渲染进程）
   └─ resources/
      ├─ app.asar                          ← 主进程 + 渲染层（main.js, src/, preload.js, icon.png）
      ├─ app.asar.unpacked/                ← 独立 node.exe 无法读 asar，必须解包：
      │    ├─ server/                      ← Node.js 后端代码（Fastify :9998）
      │    └─ node_modules/                ← 后端依赖（含 better-sqlite3 native binding）
      └─ backend/                          ← extraResources，Python Worker 全套
         ├─ python/                        ← 嵌入式 Python（Win exe / Mac framework）
         ├─ node/                          ← 独立 Node.js v22（跑后端，非 electron 内置）
         │    ├─ node.exe (Win) / bin/node (Mac)
         ├─ harness/ skills/ worker/       ← Python 后端代码
         └─ worker_main.py                 ← Python Worker 入口（JSON-RPC :9999）
```

### 运行时进程链

```
Electron 主进程 (app.asar/main.js)
├─ 渲染进程 (app.asar/src/)                 ← UI
├─ spawn(backend/node/node.exe) → Node 后端 (app.asar.unpacked/server/index.js, :9998)
│                                   └─ spawn(backend/python/python.exe) → Python Worker (:9999)
└─ better-sqlite3 (native, 在 Node 后端进程内)
```

## 2. 关键架构约束（构建必须满足）

> 这些约束来自 2026-06-23 的一次回归修复（commit `85c28f67` "cleanup" 误删了生产启动机制）。违反任一条都会导致 EXE/APP 启动即崩。

### 2.1 后端用独立 Node.js v22，而非 electron 内置 node

electron 28 自带 node 18.18，缺 `diagnostics.tracingChannel`（Node 19+ API），**跑不动 Fastify 5**。因此后端 spawn 一个独立打包的 node v22。

- `scripts/pack-backend.{bat,sh}` 下载 node v22.14.0 到 `build-backend/node/`
- `main.js` 生产模式 spawn：Win → `resources/backend/node/node.exe`，Mac → `resources/backend/node/bin/node`

### 2.2 `npmRebuild: false`（package.json `build` 段）

electron-builder 默认把 native 模块重编为 **electron ABI**。但后端用独立 node v22（**ABI 127**），重编后 ABI 不匹配（electron ABI 119）会崩。

设 `npmRebuild: false` 保留 **dev 环境编译的 ABI 127 binding**。

**前提**：dev 环境 node 必须是 v22（首次或升级 better-sqlite3 后跑 `npm rebuild better-sqlite3` 编译出 ABI 127 binding）。

**副作用（正向）**：构建**不需要** Python / node-gyp / MSVC —— 跳过 native 编译，环境要求大幅简化。

### 2.3 `asarUnpack: ["server/**", "node_modules/**"]`

独立 node.exe **不懂 asar**，无法 `require` asar 内的 JS / `.node`。必须把后端代码与全部依赖解包到 `app.asar.unpacked/`。

### 2.4 spawn cwd = `process.resourcesPath`（非 `__dirname`）

`__dirname` 在打包后是 `app.asar`（虚拟路径），Windows/macOS 无法 chdir 到虚拟路径 → `spawn ENOENT`。生产模式 cwd 必须是 `process.resourcesPath`（真实文件系统路径）。

### 2.5 `serverScript` 指向 `app.asar.unpacked/server/index.js`

同 2.3：独立 node 读不到 asar 内的 server 入口，路径必须指向 unpacked 真实路径。

### 2.6 main.js 注入 `ELECTRON_RESOURCES_PATH`

`server/lib/db.js` 用 `process.env.ELECTRON_RESOURCES_PATH` 解析 backend 目录。独立 node 无 `process.resourcesPath` 属性（那是 Electron 主进程专有），必须由 main.js 在 spawn env 里显式注入。

### 2.7 `db.initDb()` 必须在 `scheduler.startAll()` 之前（`server/index.js`）

`scheduler.startAll()` 查 `scheduler_tasks` 表，`db.initDb()` 才建表。顺序反了会 `no such table`。dev 模式因 db 文件早有表掩盖了这个 bug，生产首次启动（空 db）必崩。

## 3. 图标构建

**唯一源文件**：`D:\coding\alphawise\icon.png`（项目根目录，400×396）。**不在** `frontend/icon.png`。

`frontend/scripts/gen-icons.js` 用 `png2icons` 库从源 png 生成：

| 输出 | 用途 |
|------|------|
| `resources/icon.ico` | Windows EXE 图标（`win.icon`）、NSIS 安装器图标（`installerHeaderIcon`） |
| `resources/icon.icns` | macOS APP / DMG 图标（`mac.icon`） |
| `resources/icon.png` | Linux 图标、备份 |

窗口任务栏图标走另一条路：`main.js` 的 `icon: path.join(__dirname, 'icon.png')`，用 asar 内打包的 `icon.png`。

`gen-icons` 挂在 `npm run gen-icons`，由 `build` / `build:win` / `build:mac` 前置执行。**改图标只需替换根 `icon.png` 后重新 build**。

## 4. 构建步骤

### 4.1 前置条件

| 依赖 | 版本 | 说明 |
|------|------|------|
| Node.js | **v22.x**（dev 机） | 后端运行时 + native binding 编译基准。必须 v22（匹配打包的 node v22.14.0 的 ABI 127） |
| npm | 随 Node | |
| Python | 不需要 | `npmRebuild:false` 后构建不编译 native（dev 机只需首次 `npm rebuild better-sqlite3`） |

首次拉代码后，确保 better-sqlite3 是为本机 node v22 编译的：

```bash
cd frontend
npm install
npm rebuild better-sqlite3    # 编译出 ABI 127 binding（仅首次/升级后需要）
```

### 4.2 一键构建

#### Windows

```bash
# 在项目根目录
scripts\build.bat
```

`build.bat` 依次：① 清残留进程 ② `pack-backend.bat`（打 Python + node v22 到 build-backend/）③ `npm install` ④ `npm run build:win`（gen-icons → electron-builder → NSIS exe）

产物：`frontend/dist/灵智投研助手-Setup-0.1.0.exe` + `frontend/dist/win-unpacked/`（免安装版）

#### macOS

```bash
# 在项目根目录
bash scripts/build-mac.sh
```

`build-mac.sh` 依次：① 清残留进程 ② `pack-backend.sh`（打 Python framework + node v22，按 `uname -m` 选 arm64/x64）③ `npm install` ④ `npm run build:mac`（gen-icons → electron-builder → dmg）

产物：`frontend/dist/灵智投研助手-0.1.0.dmg`（x64 + arm64 两个）

> ⚠️ **mac 生产构建尚未实测**（历史上只实现了 Windows）。脚本逻辑已按 Windows 验证过的模式补全，但需在 mac 上首次运行时确认。

### 4.3 增量构建（跳过后端打包）

代码改动后，无需重打 Python/node（耗时长）：

```bash
# Windows
scripts\build.bat --skip-backend

# macOS
bash scripts/build-mac.sh --skip-backend
```

只同步 `backend/{harness,skills,worker,resources}` 到 `build-backend/`，然后直接 `npm run build:win/mac`。

### 4.4 仅前端改动（最快）

只改了 `frontend/src/` 或 `main.js` 或 `server/`，无需重打后端，直接：

```bash
cd frontend
npm run build:win     # 或 build:mac
```

## 5. 构建产物验证

构建完成后，**必须**验证 win-unpacked（或 .app）能真正启动：

```bash
# Windows: 双击或命令行启动
frontend/dist/win-unpacked/灵智投研助手.exe
```

启动成功的标志（控制台或 `%APPDATA%/harness-frontend/logs/electron.log`）：

```
[main] App ready, mode: production
[main] Window ready to show
[backend:stdout] [server] Fastify listening on http://127.0.0.1:9998
[backend:stdout] [db] Initialized: ...
[main] Node.js backend is ready
[main] Python Worker is ready
```

健康检查：

```bash
curl http://127.0.0.1:9998/health   # → {"status":"healthy",...}
curl http://127.0.0.1:9999/ready    # → {"status":"ok"}
```

### 常见失败排查

| 症状 | 根因 | 解决 |
|------|------|------|
| 双击无反应，无日志 | native binding 在 asar 内 / ABI 不匹配 | 确认 `asarUnpack` 含 node_modules、`npmRebuild:false`、dev 机 node 是 v22 |
| `spawn ... ENOENT` | cwd 指向 asar 虚拟路径 | main.js 生产 cwd = `process.resourcesPath` |
| `Cannot find module .../app.asar/server/index.js` | serverScript 路径未指向 unpacked | main.js 指向 `app.asar.unpacked/server/index.js` |
| `diagnostics.tracingChannel is not a function` | 用了 electron 内置 node 18 | 确认 spawn 的是 `backend/node/node.exe`（v22） |
| `NODE_MODULE_VERSION 119 ... requires 127` | binding 被重编为 electron ABI | `npmRebuild: false` + `npm rebuild better-sqlite3` |
| `no such table: scheduler_tasks` | initDb 顺序错 | `db.initDb()` 在 `scheduler.startAll()` 前 |
| `path argument ... Received undefined` | `ELECTRON_RESOURCES_PATH` 未注入 | main.js spawn env 加 `ELECTRON_RESOURCES_PATH: process.resourcesPath` |
| 卡在"正在启动服务"，worker 不 ready，日志无 `[worker] Starting` | `pythonWorker.js` 用 `process.resourcesPath`（独立 node 无此属性）→ start() 在日志前抛错 | pythonWorker.js:154 改用 `process.env.ELECTRON_RESOURCES_PATH` |
| 卡在"正在启动服务"，worker 日志报 `No module named 'encodings'` | `python314.zip`（Python stdlib）未打包 | extraResources filter **不能**含 `!python/*.zip`（会误伤 python314.zip） |
| 构建报 `icudtl.dat ... used by another process` | 旧 EXE 进程占用 dist | 任务管理器杀掉"灵智投研助手.exe"后重建 |

## 6. 相关文件速查

| 文件 | 作用 |
|------|------|
| `frontend/package.json` | electron-builder 配置（build 段）、构建脚本、asarUnpack、npmRebuild |
| `frontend/main.js` | Electron 主进程，后端 spawn 逻辑（§2.1/2.4/2.5/2.6） |
| `frontend/server/index.js` | Node 后端入口，启动顺序（§2.7） |
| `frontend/server/lib/db.js` | SQLite 层，用 `ELECTRON_RESOURCES_PATH` 解析路径（§2.6） |
| `frontend/server/lib/pythonWorker.js` | spawn Python Worker，按平台选 python 路径 |
| `frontend/scripts/gen-icons.js` | 图标生成（§3） |
| `scripts/build.bat` / `build-mac.sh` | 一键构建入口 |
| `scripts/pack-backend.bat` / `pack-backend.sh` | 打 Python + node v22 到 build-backend/ |

## 7. 当前已知限制

1. **mac 生产构建未实测**：§4.2 的 mac 路径逻辑已补全，但需在 mac 上首次验证。
2. **mac node 按单一架构**：`pack-backend.sh` 按当前 `uname -m` 下载 node。若需一次出 arm64+x64 两个 dmg，需在对应架构的 mac 上分别构建（node 官方无 universal2 发行版）。
3. **安装包较大（~258MB）**：含完整 Python + node v22。这是自带运行时的代价，换取用户机器零依赖。
